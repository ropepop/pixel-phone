# Ticket Streaming Architecture

This is the deep Pixel stream and capture note. It is not the first Ticket document.

For live Ticket page work, start from the ops checkout `workloads/ticket-remote/CURRENT.md`. The current product is: open the signed-in page, get a live ticket picture, use one visual action engine to open or register tickets and switch briefly between the newest unactivated and recently activated views, and request a control code when needed. The browser oval is optional local authorization for the same `register_current` action as the button; it is not a second phone-control protocol.

Old Ticket pictures and proof packs now live in `archive/ticket/`. Do not start there.

The older measurement history lives in [ticket-streaming-responsiveness-analysis-20260502.md](../../ops/reports/ticket-streaming-responsiveness-analysis-20260502.md). Use [Touch Brightness Architecture](./TOUCH_BRIGHTNESS_ARCHITECTURE.md) for panel-brightness ownership and [ROOT_OPERATIONS](../runbooks/ROOT_OPERATIONS.md) for general Pixel operations.

## Source Of Truth By Flow

| Flow | Success source | Failure source | Explicitly not a source |
| --- | --- | --- | --- |
| Public ViVi ticket stream | Pixel root H.264 health, fresh Pixel app-state proof, relay direct-stream freshness, and authenticated Brave visual proof for public close-out | Pixel root health, relay health, or authenticated Brave visual failure | RS Telegram result state or stale browser canvas state |
| Unified Ticket action v3 | Two agreeing fresh rooted visual observations, a proven transition, the durable Pixel dispatch journal/checkpoint, and terminal `ticket_action_v3` projection | Visual ambiguity, login/blocker/design drift, expired command, or an uncertain physical registration checkpoint | Ticket text, hierarchy labels, browser coordinates, a command row by itself, or blind retry after an uncertain tap/drag |
| ViVi control-code request | Pixel strict generated-state proof plus requester-browser freeze/capture of the rendered live stream frame | Pixel request/input failure, phone visual generated-state timeout, browser capture rejection/close, or cleanup state | Pixel/phone screenshot transfer, browser image upload, public tap/key control, root hierarchy-only result authority, broad code-like visual matches |
| RS Telegram monthly-ticket QR | Pixel RS direct tap flow plus bounded phone-side RS state proofs and one secure RS screenshot captured from the RS app | Pixel RS state-proof failure or broker deadline when no final Pixel result arrives | Brave visual proof, public relay video clients, ViVi cleanup success, black/blocked screenshot pixels |
| Cleanup/restoration | Root proof that ViVi returned to `TICKET_DETAIL` with the Aztec graphic plus a fresh frame | Cleanup completion event and attention state | Ticket-list-only proof, the nested yellow `Reģistrēt biļeti` button, or changing a result that was already delivered |

Fast paths may depend only on their owned root/source-of-truth inputs. No product path may wait on unrelated visual proof, fallback stream modes, cleanup success, or stale health summaries. Cross-path checks are allowed only after the product result has already been decided.

## 1. Startup To First Visible Frame

```mermaid
sequenceDiagram
  participant Operator as Browser
  participant Public as ticket_remote
  participant DB as SpacetimeDB
  participant Service as TicketStreamService
  participant Capture as Root capture
  participant Root as Root shell
  participant Vivi as ViVi app

  Operator->>Public: GET / and video WebSocket
  Operator->>DB: presence and control reducers
  Public->>Service: private session start / video WebSocket
  Service->>Service: check ViVi, root capture, guards
  Service->>Service: enable session protections
  Service->>Vivi: launch or confirm ticket page
  Service->>Capture: start root capture loop
  Capture-->>Service: current-epoch frames
  Service-->>Public: config + binary frames
  Public-->>Operator: shared live frames
  Operator->>Operator: decode/draw current frame
```

The Pixel serves only private health, session start/recover/stop, H.264 video-stream, and retained RS broker interfaces on `127.0.0.1:9388`; it does not serve a browser page or a public Ticket control socket. The old Pixel-local page returns the reduced-release tombstone and the Pixel-owned Cloudflare tunnel is no longer shipped. `pixel-ticket-start.sh` starts the Android supervisor and ticket service. Kitty-gration's private `ticket_phone_bridge` is the only phone transport, and kitty-gration owns public ingress.

The Android orchestrator owns a durable `ticket_service_enabled` toggle. The default is off. When it is on, SupervisorService starts and keeps checking the `ticket_screen` component after service start, package replace, and phone boot until the local ticket server is ready. This readiness path must not open ViVi or start screen capture until an authenticated viewer asks for a stream. When the toggle is off, the ticket component is not auto-started by the supervisor loop and the stop script is run to keep the server stopped. Once readiness is proven stable, periodic rechecks are throttled so the idle phone does not repeatedly spawn root pid/cmdline probes just to confirm unchanged health.

The browser marks the stream visible only after a real decoded frame is drawn. Health updates must not overwrite that visible state back to waiting.

The public browser records the broad loading path as separate phases: HTML ready, health ready, Spacetime connected, public video socket open, active session observed, stream config received, and first live frame drawn. Loading over two seconds is logged with the current blocking phase so public Cloudflare/auth delay can be separated from Pixel stream delay. The operational target for authenticated `ticket.jolkins.id.lv` is a live ViVi ticket frame in 5 seconds or less, with stream delay measured from Pixel/relay frame age and kept within the live freshness threshold.

The public relay may retain a startup-only viewer lease while serving the authenticated index shell. If the root request already carries a valid server-session cookie, the relay starts this prewarm before state rendering so phone wake overlaps the remaining page work. The current prewarm hold is 30 seconds, and the no-viewer warm stop window is 90 seconds, so reloads, brief closes, and short reconnects keep the rooted H.264 stream hot without turning the ticket stream into an always-on background viewer. The hold is a bridge for first paint and quick return, not a permanent viewer; once the real sockets attach or the warm window expires, normal viewer presence owns ticket priority.

The public service sends no-store headers for Ticket HTTP responses. Browser cache cleanup belongs to that service; the Pixel has no page assets, bootstrap endpoint, cache lifecycle, or client-log endpoint.

## 2. Browser Control And Video Lifecycle

The browser uses direct Spacetime subscriptions/reducers for presence, stream intent, control-code work, and acknowledgements. Its only media socket is the public `/api/v1/stream` H.264 socket. `ticket_remote` multiplexes viewers over one private Pixel `/api/v1/stream` upstream and uses private HTTP session endpoints as a bounded readiness fallback. Pixel `/api/v1/session` is not part of the browser product; its remaining messages are restricted to the protected RS broker flow.

Each public page includes internal viewer/page identity for diagnostics. Reloads replace that page's public connections without stopping the shared phone stream, while the Pixel sees only the bridge-owned upstream video connection.

Cold private-relay video handshakes carry only the server-owned `startup_` correlation: an eight-hex one-way derivative of the in-memory startup trace, never the browser session, viewer, full trace identifier, or authentication material. Pixel validates that exact bounded shape and binds it before recording the bridge video-client open or starting the local ticket session. The same correlation remains optional on the durable Spacetime start command, so either side may roll forward independently and the durable command stays the fallback.

Control and video socket identity includes the browser page version. Health exposes active client identity/page-version diagnostics so public verification can prove the current Brave tab is running the latest served page rather than a stale cached shell.

The phone owns viewer inactivity truth and timeout enforcement, but the browser owns smooth countdown rendering. The phone sends an immediate inactivity update when activity changes, then broadcasts the steady countdown every five seconds until the final minute, where it returns to one-second updates. The browser fills the visible timer locally between those phone updates so passive ticket viewing does not keep the Pixel sending countdown rows/messages every second.

Reconnect behavior:

- Page reload and ordinary tab close are reconnect-friendly and should not stop the phone session.
- Explicit Stop is deterministic: stop capture, close clients, disable protections, and prevent old browser sockets from auto-starting the stream again.
- A visible, focused browser page is allowed to recover a phone/backend stream that was killed by inactivity or relay loss. Hidden or unfocused pages must not resurrect the stream on their own.
- A restored old/cached visible page opens the public video socket, reconnects Spacetime state, publishes focus, and requests the first keyframe immediately. It does not wait on the early-socket grace timer, stale reconnect timer, first-keyframe minimum interval, or a one-second activation retry before starting recovery.
- Slow video clients are isolated from frame production. Stale frames may be dropped for that client so the newest independent frame stays fresh.

Legacy clients without viewer/page identity should still connect, but they do not get same-viewer replacement.

## 3. Pixel Capture, Root Frames, And Browser Draw

The accepted production public capture path is root-only hardware H.264 over the existing authenticated video WebSocket:

- Pixel output format: H.264 Annex B access units from the rooted hardware `MediaCodec` input-surface encoder, reported as `captureMode=root_hardware_h264`, `transport=h264-annexb-websocket`, and the exact `avc1.*` codec string when SPS is observed.
- Arbuzas output format: `ticket_remote` forwards the single private Pixel H.264 stream to authenticated viewers over `/api/v1/stream` without decoding or re-encoding.
- Default quality profile: 994x2046 root hardware H.264 at about 8 Mbps, cropped to the same browser-visible ticket view as before. Capture is fixed at one frame per second and every emitted frame is independently decodable. H.264 pads that visible frame to 1008x2048, keeping both the coded-pixel and Level 4 macroblock allocations inside their established ceilings. Codec, crop, BT.709 limited SDR signalling, and the single-encoder contract remain fixed.
- Runtime: Pixel owns root capture start/stop, hardware keyframes, stream epoch, frame sequence, and fixed capture cadence. `ticket_remote` is a latest-frame fanout, not a media processor.
- Cadence: the helper uses an absolute monotonic one-frame-per-second scheduler and grants at most one capture per decision. The first explicit refresh after a periodic frame may produce one immediate independent frame; presenting it starts a new one-second period, so later requests in that period coalesce. The helper exposes no runtime cadence reconfiguration.
- Independent frames: `MediaCodec` is configured at one FPS with a zero-second I-frame interval, and the helper requests a sync frame for every input. Pixel advertises the exact contract as `fps=1`, `sourceFps=1`, `keyframeIntervalFrames=1`, and `frameDependencyMode=all_intra`. Any unexpected delta output is counted and dropped before fanout, then requests a coalesced sync refresh. Persistent absence of valid output remains owned by the existing liveness watchdog rather than a new delta-specific restart loop. Health reports encoder configuration, wall-clock frame age, independent-frame counts, unexpected deltas, and recovery requests without recording pixels.
- Browser draw: the public page receives `tsf2` H.264 frames, decodes them with WebCodecs, and draws the newest decoded frame to the stream canvas. Every accepted Pixel media frame is independently decodable, so the relay may keep only the newest current-epoch frame per browser and never lets one slow socket block the phone or another viewer. Startup tracing calls a frame forwarded only after one originating viewer's bounded writer has completed its WebSocket write; relay receipt remains a separate earlier phase, and browser decode/draw remain later phases. The browser sends cumulative epoch/sequence, decoder-queue, rendered-age, and visibility feedback; it does not control bitrate, resolution, color, or codec.
- Sent ViVi ticket media excludes the existing 200-source-pixel top strip. It crops four source pixels on the left and three on the right and bottom: the native display's one-pixel ring plus the live-proven filtered-sampling guard and one final polish pixel on each of those three edges. The guard prevents the filtered 1080-to-994 draw and H.264 4:2:0 chroma sampling from carrying the saturated source edge into encoded outer pixels. One explicit `4/200/3/3` source rectangle is scaled into the configured encoded dimensions and is shared by MediaCodec drawing, visibility probes, Ticket classification, control-code classification, and geometry detection. Pixel reports all four crop edges plus the visible source size in stream config/health. Every detected tap/drag target, including the slider, registration control, activated-status marker, Back, popup, Submit, and close targets, is mapped back through that same rectangle before phone input; browser slider geometry is normalized against the encoded cropped frame.

The normal public stream path must not depend on Android MediaProjection, Android screen-recording permission UI, WebRTC, AV1, H.265, PNG frame streaming, FFmpeg H.264, software stream fallback, or accessibility fallback. If the rooted hardware H.264 path cannot run, the public page shows a clear unavailable/attention state rather than silently changing capture modes.

Earlier measured paths are documented for context only. Root-fed AV1 was too slow for production. Root FFmpeg H.264 improved capture cost with the native helper but had authenticated-browser decode failures. Root PNG was clear but full-resolution capture was too slow and CPU-heavy for the requested freshness target. WebRTC was removed from the current production path in favor of the simpler H.264 WebSocket pipeline.

Frame freshness:

- The current frame envelope is `tsf2`: stream epoch, frame sequence, frame timestamp, and keyframe flag precede the encoded video payload. Under the current all-intra contract, every accepted media envelope has its keyframe flag set.
- Stream epoch changes on capture config changes, capture restarts, and stop/start boundaries.
- The browser and public relay drop frames from old epochs, duplicate or lower frame sequences, and legacy frames once `tsf2` has been negotiated.
- Per-client pending slots and write generations are cleared on reconnect, reload, config change, stream epoch change, and decoder reset so old frames cannot leak into a new view.

Fresh-frame behavior:

- Browser/reload/control-code transitions request one coalesced fresh current-epoch independent frame from the running Pixel encoder.
- Keyframe requests during startup must not restart the encoder while it is already waking or preparing.
- Keyframe requests that arrive while the Pixel stream is inactive are held as the pending startup keyframe for the next capture start instead of being treated as wasted recovery noise.
- A duplicate `/api/v1/session/start` during root hardware startup must return the existing `starting` state while wake/root proof is still pending. It must not mark the session `live`, start/restart the encoder, or emit `session_start_already_active` until wake proof has verified ViVi ticket detail and hardware frames have been allowed.
- Recent config can be sent to new viewers immediately. Recent independent frames can be reused only when they are from the current stream epoch and inside the freshness window. Old cached frames must never be drawn.
- If no fresh same-epoch frame exists, the relay/browser requests a coalesced hardware refresh instead of replaying old video.
- `ticket_remote` keeps at most the newest pending independent frame per video client, so slow viewers cannot delay the current view for everyone else.
- During a control-code request, `ticket_remote` keeps the normal shared stream live. Other authenticated viewers may briefly see the real phone open ViVi's control-code UI, but no viewer receives private phone control or a separate control video stream.
- Restart reasons, suppressed restart requests, keyframe requests, frame sequence, and Pixel ticket events are exposed in health.
- Stop/cleanup stops the active root hardware capture path, clears the current stream epoch/cache, and leaves the ticket service ready for the next authenticated viewer.

Browser decode behavior:

- The browser decodes H.264 from the video WebSocket with WebCodecs and renders the latest accepted frame to the stream canvas.
- On stream epoch changes, the browser resets decoder state and rejects old frames. When decode falls behind, stale frames are skipped and a refresh is requested.
- Watchdogs can request a coalesced independent refresh when the visible frame is stale without leaving the streaming state.
- Video socket failures reconnect the affected browser video path. They should not restart the shared phone stream while the Pixel relay is connected and the hardware encoder is waking or already running.
- Control and video socket open timeouts are intentionally short so the page leaves long connecting states quickly. A two-second loading budget triggers video recovery, then escalates if the stream still does not produce a live frame.

## 4. Request Contracts And Safety Gates

### Unified Visual Ticket Action Contract

An already-focused ViVi activity is not relaunched before the initial visual observation; a missing focus still gets one guarded launch, and registration rechecks ViVi focus again at its final dispatch boundary.

- The signed-in browser writes one durable `ticket_action_v3` command directly to SpacetimeDB. Its targets are `open_latest_unactivated`, `open_latest_and_register`, `register_current`, `show_recent_activated`, `return_to_latest_unactivated`, `redetect_latest`, and the non-mutating `prove_current`. The server remains the authentication and video relay boundary; it is not an immediate Ticket command hop.
- Ordinary non-registering v3 navigation, re-detection, and view-switch actions publish only the v3 action projection and acknowledgement. Pixel no longer reads or writes the retired ticket-interaction claim/progress row. Registration geometry travels only with the current v3 proof projection, while successful registration retains the dedicated activation checkpoint and commit path.
- The Pixel subscribes to every pending Ticket automation row and hands subscription and reconnect polling candidates to one dispatch ledger. Polling is recovery only. `ticket_action_v3` has a dedicated priority subscription consumer, so a keyframe waiting for stream startup cannot delay warm action observation; both consumers still claim the shared ledger before phone handling. After a terminal acknowledgement, the ledger retains a bounded 15-minute ownership tombstone (up to 1,024 entries), longer than the 10-minute command lifetime. A stale pending poll row therefore reuses and re-acknowledges the terminal result without re-entering the phone handler; a stale subscription delivery is read-only and cannot publish terminal state. Active or unacknowledged ownership is never pruned. A phone mutation is never repeated without reconciling its durable journal, activation checkpoint, and a fresh visual observation.
- Every mutating action holds the one phone-mutation lane and advances one proven transition at a time. It also acquires one action-scoped raw-panel-dark lease before any ViVi launch and retains it through visual waits, navigation, Accessibility registration, terminal proof, and final convergence. `prove_current` is the only read-only exception: it takes neither the mutation lane nor panel-dark lease, and is fenced by the V3 action generation, mutation generation, rooted physical-touch generation, capture epoch, and capture restart count. When an explicit V3 request arrives, its Spacetime reducer transaction terminalizes only pending/running `prove_current` rows and commands before applying the normal phone-lane admission; it never supersedes another mutation. Pixel then cancels and joins the running proof before entering the mutation lane. After a dispatched navigation tap, one bounded read-only convergence tail may continue observing the same journaled transition when the first proof window expires; it never repeats the tap. The helper writes panel brightness zero every 5 ms and an independent reader confirms zero every 250 ms. The required 2.5-second post-mutation convergence window begins at the latest possibly dispatched mutation, so terminal visual proof overlaps it and release waits only any remaining interval before the unchanged exact-zero and helper-shutdown proof. A root-confirmed physical touch cancels the lease immediately: before dispatch the action stops, while after a possible tap or drag it becomes attention-needed and is never replayed. `finally` releases the helper on success, failure, cancellation, timeout, and normal service replacement; the helper also exits when its exact Android owner PID/start time disappears, and startup removes marked helpers left by an abrupt prior process before Ticket command subscription begins.
- The rooted stream detector classifies activated detail, unactivated detail with slider bounds, ticket lists with card/action bounds, the ViVi route-planning home with a proved Tickets-tab target, the empty Single-use Tickets shell with a proved Time-tickets-tab target, control-code surfaces, login, blockers, and unknown layouts. Ticket-list chrome takes precedence over slider-like card geometry only after the separated selected-tab underline and wide red/orange route-card header bands are both proved; without that list proof, a slider also requires the ticket-detail graphic or its unique top-right close, otherwise the frame remains unknown. Route-home authority requires the full lower navigation separator, selected Home glyph, and separate neutral ticket-shaped Tickets glyph in two agreeing frames. The earlier route layout may additionally prove its wide orange action; the current root layout instead requires independent neutral Profile and three-line Menu glyphs and rejects any Tickets-tab underline. Empty Single-use authority additionally requires the left-only selected underline, both bounded tab-label silhouettes, the central empty-state silhouette, no ticket action/card color, and the selected bottom Tickets glyph. A mutating v3 navigation action journals exactly one proved tab tap before dispatch, re-observes, and continues only from a typed Tickets shell/list; unchanged Home or any ambiguous transition becomes attention-needed and is never replayed. The Time-tickets list is always an intermediate state: every card or status target used for input needs two fresh frames agreeing on both identity and geometry, and a successful terminal or retained result must match the target's activated/unactivated Aztec-detail view. `register_current` rejects both intermediate states, and non-mutating `prove_current` reports them without input. The lightweight visibility probe accepts a sparse dark ViVi page only when it still has sufficient luminance range, mean, dark coverage, and at least eight independent bright samples; uniform black and navigation-pill-only capture remain blocked. Ticket actions do not use UiAutomator or accessibility labels for state, navigation, card selection, registration, or control-code target geometry. Rīgas Satiksme keeps its separate automation authority.
- In the current ViVi monthly-ticket list, the separately detected orange registration control opens the unactivated slider for the next journey, while a dedicated compact registered-status target opens the most recently activated journey. Open, combined-register, return-to-unactivated, and re-detect use registration-control geometry. View-recent-activated and control-code preparation require the dedicated registered-status geometry; they never fall back to a generic dated card body. The transition is successful only after fresh activated detail with its Aztec graphic is proved, so a plain ticket list is never terminal success for activated-detail navigation.
- Ticket-list choice uses the bounded digit/date recognizer only on demand. Two distinct fresh frames must agree on a parseable, confident, uniquely eligible current-or-upcoming card. Conflicting, duplicated, expired, unreadable, rotated, overlaid, or redesigned layouts fail closed.
- Registration uses the visually detected slider bounds and exactly one uninterrupted 800 ms Accessibility stroke after a fresh unactivated-detail proof. The Accessibility service is made ready before that final proof is bound; if it disconnects afterward, the action fails before dispatch instead of waiting on a stale proof. ViVi must still own Android's focused accessibility window at the dispatch boundary. The full-display accessibility brightness shield is suspended for only that stroke because adding or updating it can trigger a WindowManager/display-policy transition while Flutter owns the drag; concurrent brightness reassertions retain their logical request but cannot re-add the window until the stroke is terminal. The independent action root clamp and one-pixel application shield keep the panel at zero, and the full-display shield converges to its latest requested state before visual reconciliation. A hide failure rejects the stroke before dispatch, and a restore failure is uncertain after dispatch. V3 has no segmented start/continuation handoff and never locally replays a stroke. Android cancellation or timeout is uncertain and is reconciled visually once; if that reconciliation proves activated, Pixel returns success so the normal Spacetime activation commit completes. A completed stroke that leaves the exact same unactivated detail records the durable phone stage `no_transition_proven` and reports `ticket_action_gesture_completed_no_transition`. Only Spacetime may admit one separately identified child command from that conclusive parent result; unknown, conflicting, preempted, or uncertain results never authorize it. The list-card identity and a separate phone-local salted signature of the stable lower route/date metadata band remain distinct throughout reconciliation; the upper crop boundary, rotating ticket-code graphic, and slider are excluded. `register_current` may refresh an idle frame/geometry proof only when two fresh detail frames still match that exact signature and helper epoch. A blank or changed signature fails closed with a privacy-safe identity-conflict reason, and a helper-restart signature fails closed instead of rebinding the action to another open ticket. On restart, `dispatching`, `no_transition_proven`, or uncertain state becomes attention-needed; `proven` or committed state is recovered and acknowledged without another drag.
- `prove_current` requires an already-running fresh capture, observes two distinct agreeing fixed-cadence frames with coalesced immediate refresh requests, and never launches ViVi, changes brightness, takes the phone lane, navigates, recognizes list dates, taps, or drags. An unactivated detail publishes a normal successful `latest_unactivated` action proof and the matching normalized slider bounds. Activated detail, list, login, blocker, and stable unknown states publish only their sanitized view/reason and never authorize registration. A mutation admission or rooted physical touch during observation invalidates the proof instead of delaying the explicit action.
- A successful activation stores only the opaque visual anchor needed for safe navigation; the phone does not calculate or persist the business switch window. SpacetimeDB owns the 15-minute switch policy and supplies its `policyRevision` and `switchExpiresAt` on each authorized switch action. Pixel requires that authority plus unambiguous recent-activated and newer-unactivated visual anchors, echoes the supplied deadline, and fails closed when authority or visual evidence is missing. Pixel's monotonic execution deadlines, command expiry checks, at-most-once dispatch journal, and activation checkpoint remain execution-safety mechanisms rather than product-policy timers.
- The public action projection is sanitized to action id, target, status, phase, current visual view, switch state/expiry, proof watermark, fixed safe reason, and timestamps. A separate short-lived slider row may expose only 0–10,000 basis-point bounds relative to that exact encoded frame, tied to proof action id, stream epoch, and frame sequence. The current service reducer atomically commits a terminal action plus its optional normalized region. During additive rollout Pixel falls back to the prior idempotent action-then-geometry reducers when an older module rejects that reducer; the safe normalized region remains in the terminal journal, so either retry repeats metadata only, never phone input. Dates, ticket text or numbers, glyph output, screenshots, raw pixels, raw device coordinates, and private diagnostic errors remain on the phone.

### Public ViVi Control-Code Contract

The public browser no longer claims phone control. It can only submit a numeric control-code request:

- The public page opens a local dialog, accepts only 2-8 digits, and posts the request to `ticket_remote`.
- `ticket_remote` authorizes the requester through ticket membership, applies the two-requests-per-60-seconds limit, queues requests, and runs only one phone job at a time.
- The browser opens the local dialog immediately and accepts valid 2-8 digit input without waiting for video, phone readiness, or preparation. It starts the one page-owned SpacetimeDB connection during authenticated startup; submission waits only for that connection's current generation to become live, with one two-second admission deadline, and calls `memberRequestControlCode` exactly once. Ordinary rendering, focus changes, and fast-state expiry never launch preparation or recovery. Each request carries the current fast-state revision or an empty revision when cold/stale.
- The phone receives only `generate_control_code` with the request id, digits, requester identity, server timestamp, and fast-state revision. The browser never sends tap coordinates, keyboard events, ADB commands, screenshot bytes, or direct phone-control messages. Pixel is the only phone authority and accepts either a valid current revision or the same single inline preparation stage; there is no preparation reducer or compatibility command.
- Pixel executes one ordered request state machine: validate; claim the phone lane; start the request-owned keyboard clamp asynchronously; validate the revision; perform one strict rooted visual preparation when needed; prove and retain the current activated or unactivated detail's phone-local static identity; tap its freshly detected ViVi control; prove the popup and its field/button geometry; wait for the clamp; focus the proved field; enter and visually prove the digits; re-detect the value-bearing popup and tap that fresh `OK`; prove the non-refreshing generated Aztec plus its black digits strip and close badge; publish a following-frame watermark; wait for browser paint acknowledgement; re-prove and tap only that result badge; prove return to the exact original detail; publish the next fast-state revision; release the clamp. No stage may skip or infer another stage.
- The fast-state coordinator is keyed by the current stream epoch. A matching revision is reusable only when its epoch, frame sequence, fresh rooted raw-ticket marker, live H.264 stream, and cleanup state all agree. Otherwise the request performs one bounded four-second preparation pass. Preparation recognizes only fresh rooted states: activated ticket detail, a ticket list with one dedicated registered-status target, a stale popup, a stale generated result, or ViVi outside the foreground. It uses the detected registered-status target or badge cross exactly once, never a generic card body, the yellow registration button, or ticket-header close, and fails closed for login, registration, empty-list, ambiguous registered targets, unknown, blank, or account-mismatch screens.
- The Pixel is the source of truth for observed app state. It emits `ticket_state_event` messages for raw ticket, popup open, generated result visible, returning to raw, raw return complete, and attention-needed states. Each event carries the request id when relevant plus stream epoch, frame sequence, and phone timing. A fresh activated or unactivated Aztec-detail observation is already a valid control-code starting surface: Pixel retains that exact private detail identity and taps its visually detected ViVi control directly. It never backs out to the Time-tickets list merely to start control-code generation. Lists remain bounded recovery-only intermediates when no detail is visible and are never successful control-code states. The direct worker gives the command and matching acknowledgement priority over diagnostics without creating a second startup path or a phone-local business-policy deadline.
- Pixel opens ViVi's control-code popup with one rooted button tap, then acquires a request-scoped soft-keyboard suppression lease through Android Accessibility's `SoftKeyboardController`. The lease records only ownership and the previous show mode in a phone-local recovery marker, proves `SHOW_MODE_HIDDEN`, and is validated again immediately before entry without silently reacquiring after preemption. The bundled native root helper then focuses the visually proved input position and runs one Android InputManager key-event batch: move to end, eight deletes, and the validated digits. It never creates an input device, changes enabled/default IMEs or hardware-keyboard settings, sends Back, Tab, Enter, or another form-activation key. A visible software keyboard fails closed. Submit remains a separate rooted tap after two fresh visual proofs, and focus is cleared before the original keyboard show mode is restored. Service reconnect recovers a stale owned suppression marker; cancellation, timeout, cleanup, and service replacement use the same bounded restore path. The helper writes no digit-bearing file, securely scrubs digit buffers, and never exposes the root command/output to health or logs. Two distinct fresh rooted H.264 samples use a dedicated 96x144 submit probe to prove the value in the stable unshifted popup. Pixel then takes two more agreeing value-bearing popup samples and derives a fresh enabled `OK` target from those frames before it taps. The probe recognizes both the earlier light/orange sheet with nearly-black digit strokes and the current dark/blue sheet with bright digit strokes, while rejecting ViVi's gray placeholder and a one-column caret. A bounded four-probe window tolerates an initial transition-frame `unknown` or timeout, while two consecutive blank samples are required before retyping; a shifted keyboard layout fails immediately. Raw ticket, generated result, or an exhausted ambiguous window blocks Submit. Accessibility is used only to suppress and safely restore the software keyboard, never to classify Ticket content, navigate, enter digits, or submit.
- After OK, the Pixel asks the running rooted H.264 helper for strict fresh visual state. Success requires two distinct `GENERATED` probes agreeing on the detected black digits strip, close badge, salted non-refreshing Aztec signature, and helper epoch. Returning to the same ordinary activated or unactivated detail, popup disappearance, a changing ordinary Aztec payload, a status strip without a stable generated code, or a generic frame change is not generated-result proof and fails closed. If the same popup remains visible, Pixel permits exactly one retry only after two new samples again prove the entered value and fresh enabled Submit button. That retry taps Submit only; it does not clear or mutate the already-proved value. Two more popup samples after the retry fail quickly as `control_code_submit_still_open` instead of waiting on a slow hierarchy dump.
- On the normal success path, Pixel sends only rooted visual proof and frame-watermark metadata. Immediately before watermarking, it repeats the same two-frame generated-badge proof and publishes `resultProof="phone_visual_generated_with_close"`. Each exact rooted probe remains outstanding for a bounded multi-frame reply window before another probe can replace it; the overall re-proof remains bounded and still requires two distinct agreeing frames. `phone_visual_generated_inline` is reserved for a future dedicated inline-layout detector and must not be inferred from ticket identity or Aztec motion. Pixel, Spacetime, and the browser use the same allowlist, and Pixel must not send screenshot bytes, OCR, or raw code content for the user-facing result.
- `ticket_remote` treats Pixel image results as disabled for ViVi control-code. A requester result becomes complete only after the requester browser has rendered a stable generated frame at or after Pixel's marker and accepted the browser-local freeze/capture proof.
- The requesting browser freezes the exact proven live stream frame, rejects entry-popup, dim-overlay, keyboard, and fade/ghost frames, and captures a stream-resolution result image locally. It acknowledges that capture only after the image has decoded, remained visible and inside the viewport for two browser paint frames, and emitted `control_code_frame_painted`; assigning an image URL or preparing a hidden provisional frame is not success. The requester-only browser image then remains pinned while Pixel cleans up. The public API still never uploads browser image bytes.
- Cleanup keeps the public control-code queue blocked until browser capture is acknowledged and fresh visual state is confirmed. Pixel obtains two new `GENERATED` observations agreeing on the same close badge and generated-code identity, taps that badge once, and then requires two fresh action observations to agree on the exact original activated or unactivated state, static detail anchor, and ViVi control geometry. Missing mode, missing or changed identity, missing or changing badge geometry, helper-epoch change, or a return to the ViVi route root fails closed and never falls through to Back or reports raw-ticket success. The ticket-header X and yellow registration button are never cleanup targets. A later V3 action may separately recover from a visually proved route root through its own one-tap journal. No browser coordinate, screenshot transfer, accessibility, hierarchy authority, list-only, broad-recovery, or background-preparation path exists. After the browser-capture command is accepted, the direct worker keeps a request-id-scoped outbox consumer active for the whole bounded visual-close and panel-finalization budget and publishes the first matching raw-detail or cleanup completion immediately. It no longer abandons that handoff after 1.2 seconds. A fresh raw-detail handoff calls one Pixel-only Spacetime reducer that clears the exact request barrier and publishes the matching ready watermark atomically; the two legacy idempotent updates are used only while that additive reducer is genuinely unavailable. An acknowledgement timeout is an explicit failed request and still uses this same strict cleanup stage; success requires the acknowledged frame, completed cleanup, and a new fast-state revision. The durable cleanup-pending bit blocks replay and new requests across a process restart; the phone-local result mode and salted detail identity are intentionally not replay authority after a helper-epoch change, so such recovery remains attention-required until an explicit fresh visual reopen proves readiness.

### RS Telegram Monthly-Ticket Contract

Rīgas Satiksme Telegram QR jobs use the retained private Pixel RS broker socket and require explicit `owner="rigassatiksme"`, `app="rigas_satiksme"`, and `flow="monthly_ticket"`, so they remain separate from ticket.jolkins ViVi control-code requests. The broker keeps the public `POST /api/v1/qr/jobs` API compatible, but groups waiting RS jobs after a 250 ms burst window and sends the phone one `generate_rigassatiksme_qr_batch` command, including for a single RS request. The batch payload carries `batchId`, `jobs[{requestId,digits,createdAt}]`, owner/app/flow, and the current ticket-priority state. Pixel emits one `rigassatiksme_qr_result` per request id; the broker completes each job independently, accepts out-of-order results, reconnects and resends only unfinished batch jobs when the phone socket drops before deadline, and uses RS-specific batch health for disconnected final reconciliation. The shared ViVi `controlCodeRequest` health bucket is ViVi-only and must not finalize, retry, or rename RS jobs. The Pixel RS path is a direct state-gated tap lane with bounded phone-side state proofs. Pixel launches `com.flutter.rspassenger`, waits briefly for foreground, and takes an RS app `uiautomator` state proof before touching the app and after each meaningful transition. The classifier recognizes both English and Latvian RS monthly-ticket screens, including `30 dienu biļete`, `KONTROLES KODS`, `Reģistrēt braucienu`, `Ievadīt kodu manuāli`, `Ievadi kontroles kodu`, `Atcelt`, and `OK`. If the first state is unknown, Pixel performs exactly one bounded force-stop/relaunch without clearing RS app data, rechecks state, and stops before code entry with `rs_app_attention_required` if the app is still unknown. Old control-ticket screens must be closed and rechecked before registration can start; if Back does not clear the old control-ticket screen, Pixel does one no-data-clear RS relaunch and rechecks before deciding app attention. Registration, manual-entry, typed digits, and final submit must each be proven before the next action; visible node centers are preferred for safe taps, with fixed coordinates only as guarded fallbacks after state is known. Final unknown proof after submit becomes `rs_app_attention_required` after one recheck. This shape is used because live RS verification showed screenshot pixels can be black/blocked and full semantic loops are too slow when every action waits for a 2.5-second `uiautomator` dump, while blind middle-section tapping can leave RS showing the previous QR. The final Telegram image remains a separate secure RS screenshot capture after state proof. Normal RS generation must not depend on public viewer state, Brave, public relay clients, or ViVi cleanup success.

The success authority is an RS app shell-state proof: a control-ticket screen whose RS node text includes English or Latvian control-code markers (`TICKET FOR CONTROL`/`KONTROLES KODS`), QR text, a monthly marker such as `1 MONTH` or `30 dienu biļete`, and the submitted digits. Every request in a batch is freshly re-registered; an already-visible matching QR is treated as stale state at request start, not as success. After the requested digits are visibly proven in the manual-entry field and OK has been tapped, a nonmatching control ticket is a fail-fast `rs_monthly_ticket_stale_code`: broker and bot must not hide it with a retry, and the bot must not send a stale image. Returning to the manual-entry/manual-choice/register-trip/home surface after submit becomes `code_rejected_by_rs`; direct wrong-code text is also reported as `code_rejected_by_rs`. Missing app fields, launch/foreground failures, missing monthly tickets, authentication blocks, stale final proof, and app-attention failures remain distinct reasons and must not be collapsed to `phone_timeout`; `rs_monthly_ticket_unknown_state` is a legacy fallback, while new persistent unknown RS app states should report `rs_app_attention_required`. The returned Telegram artifact is the secure Pixel-captured monthly-ticket screenshot, captured at a bounded readable width for speed (currently 720 px maximum) and trimmed only at the shared broker delivery boundary by cropping 5% of the source screenshot height from the top and 5% from the bottom; it does not use the ViVi control-code graphic crop, a QR-only crop, a bot-side second crop, or an Android-side top/bottom delivery crop. Missing, blank, or invalid secure capture fails quickly with `rs_monthly_ticket_image_capture_failed`. Successful and final-failed RS jobs send their result to the broker immediately. Pixel returns to ViVi only after the batch is empty, ticket priority interrupts, or the phone enters an unrecoverable state; non-critical cleanup is outside the user-visible RS result timer. Public ticket viewer presence and ticket leases are hard higher-priority ownership signals for their full active duration, not bounded grace windows; they may preempt/retry unfinished RS work without burning an RS attempt budget, and while active the phone should remain on ViVi/ticket work. The measurement target is every request in a three-code burst receiving a final RS image or named final failure within 15 seconds of broker enqueue, including the burst wait. Because cleanup is after user delivery and production ViVi root dumps can take several seconds, RS return-to-ViVi keeps the dedicated 45 s budget with six focused recovery actions so a slow ticket-list/card reload can still reach `TICKET_DETAIL` without changing the normal fast ticket wake limits. A successful RS return refreshes the Pixel's recent `TICKET_DETAIL` proof so the next authenticated public viewer can use the fast ViVi foreground path instead of paying a long recovery cycle.

RS Telegram delivery is not a public-viewer decision. Brave screenshots, public canvas state, public relay video-client presence, and public ticket verification cannot turn a valid Pixel RS proof/capture into failure, and they cannot turn a missing RS proof/capture into success. If the broker receives no final Pixel result before its deadline, it may report `phone_timeout`; if Pixel sends a phase-specific RS failure, broker/bot messaging must preserve that reason.

### Result Vs Cleanup

The product result and cleanup are separate decisions. RS image delivery is final once the broker accepts a `rigassatiksme_qr_result` with valid RS app image bytes and the expected source/flow. ViVi control-code delivery is final once `ticket_remote` accepts requester-browser capture proof for the active request, and the browser may send that proof only after its decoded image passes the two-frame visible-paint check. Cleanup is allowed only after browser proof, explicit close acknowledgement, or a named browser-capture failure. Pixel runs the long ViVi generation job off its direct Spacetime command worker so browser-capture acknowledgements can be consumed while the phone result is held. `ticket_remote` keeps publishing that acknowledgement until Pixel reports cleanup, because a successful database write is not treated as phone receipt. Cleanup failure after accepted browser capture records attention-needed state instead of delaying, revoking, or renaming the already accepted request. A generic `raw_ticket` label or a changed rotating Aztec is never promoted into success: the result requires the causal Submit transition plus two matching probes of the stable generated code, digits strip, and result X; that freshly re-proved X is the only cleanup tap after browser acknowledgement.

Safety gates:
- 2026-07-10: Live end-to-end verification caught a control-code popup left open after the immediate macro tapped the keyboard-shifted OK position before the popup animation had settled. The same incident exposed sub-second `uiautomator` budgets that the guarded dump helper deliberately rejects, no terminal diagnosis for repeated visual `unknown`, weaker failure/exception cleanup, and page-ready preparation that reported warming without scheduling work. Production now keeps Submit outside the opening action, uses viable guarded root budgets, performs only bounded event/terminal root confirmation rather than polling, gives every outcome the same ticket-detail recovery fallback, and runs non-blocking preparation as real background work. The later keyboard-free path supersedes keyboard-shifted Submit for normal generation while retaining shifted-popup classification for diagnosis and recovery.

- The Pixel normalizes known ViVi states before automation. An already-open control-code popup is a valid submit state. A generated Aztec/result screen is never an idle-ready state; it is closed through the same root-only return-to-raw routine before a new request starts.
- The Pixel refuses only when root cannot inspect/control ViVi or raw-ticket return cannot be confirmed within the bounded routine. The old recoverable “refreshing ticket view, try again” path must not be used for known popup/result states.
- Duplicate request ids replay the cached result and do not execute the phone flow twice.
- Control-code automation is serialized by a Pixel-side mutex as well as the public queue, so overlapping requests cannot interleave physical phone actions.
- During the popup/result transition, foreground/page guards may observe and record state but must not force-stop ViVi, navigate back to Orchestrator, or run fresh reset.
- Cleanup failure records attention-needed and keeps public browser input blocked rather than exposing direct control or starting a new request.
- Active ticket sessions hold the Pixel screen awake and request a wake only if the display is non-interactive, unless touch brightness is enabled. When the screen is already interactive, public stream startup skips the wake key and relies on the wake lock, avoiding a repeated 1-2 second wake command on ordinary stopped-stream reloads. When touch brightness is enabled, touch brightness owns the screen hold and panel writes. Input remains blocked while the display is not interactive; the wake path is used to restore the live stream instead of launching recovery loops against a black/dozing screen. When all viewers detach or the stream stops, the ticket service releases this bright wake lock immediately; the brightness guard may keep the panel dim only when touch brightness is disabled.
- Foreground/page recovery remains fast during startup, recovery, control-sensitive work, and confirmed foreground violations. After the stream is live and ViVi ticket detail has been confirmed, the stable foreground check backs off to five seconds so passive viewing does not keep paying the startup/recovery guard cost.

Control-code request health reports the last request id, digit count, command owner/app/flow, last rejected command owner/app/flow/reason, status, reason, phase timings, root-observation time, phone visual state/proof time, browser-capture acknowledgement time, result-delivery time, total duration, duplicate replay count, cleanup status, and completion age. Public bridge health also reports the latest control-code relay-preparation result and duration plus browser capture fields such as capture-required, capture acknowledgement/rejection, candidate frame epoch/sequence, generated-chip proof, popup-frame rejection, and result-window-closed reason. Do not restore Pixel/phone screenshot delivery for ViVi control-code, public tap/key forwarding, browser image upload, root-hierarchy-only generated-result authority, accessibility-driven control-code entry/Submit, broad accessibility-driven navigation or clicks, software stream fallback, or weaken protected-edge blocking, foreground checks, notification lockdown, secure-window handling, or control-code cleanup verification without updating this document and the relevant tests.

## 5. Stop, Cleanup, Reconnect, And Tunnel Behavior

Stop paths:

- Explicit browser Stop calls the session stop endpoint with `explicit=true`.
- Service stop clears stream state, stops active capture/encoding, closes clients, disables notification lockdown, disables secure-window bypass, and clears active control-code request state. With the durable ticket service still enabled, browser Stop keeps the local service and tunnel ready but does not start ViVi or capture again until a viewer asks.
- During streaming and after a session ends while the durable ticket service remains enabled, the ticket brightness guard enforces safe dim panel brightness only when touch brightness is disabled. When touch brightness is enabled, the ticket guard parks, reports that touch brightness owns panel brightness, and does not write or restore panel brightness. Saved ticket brightness is restored only when ticket service is turned off, touch brightness is not owning the panel, or the phone is intentionally handed back to physical use.
- After explicit Stop, health should report inactive stream, zero clients, no active control-code request, and no active app-owned capture process.
- A stopped or idle stream must actively close leftover Pixel video sockets before accepting a fresh start request, and the private HTTP session start must return within a bounded timeout instead of hanging behind stale cleanup.
- Stopping capture clears old frame counters, frame ages, dimensions, bitrate, and helper state that would otherwise make inactive health look like it is still sending frames.
- Viewer inactivity timeout is also a non-destructive stop. It may stop capture, close clients, and block browser auto-start until a fresh viewer request arrives, but it must not schedule fresh ticket recovery, force-stop ViVi, or navigate back to Orchestrator.

Reconnect paths:

- Page reload should replace same-viewer public sockets without interrupting the shared phone stream.
- If all Pixel-side relay clients disconnect or the public relay goes idle, the service parks capture: it records detach state, stops the root hardware H.264 helper, disables protections, keeps ViVi available, and enforces dim brightness only when touch brightness is disabled. It must not run ViVi recovery loops while no viewer is present.
- Before cached durable demand may restart an inactive Pixel session, the worker re-reads the authoritative desired-state row. A newer zero-viewer revision suppresses the stale start and refreshes the phone report, so the end of reconnect grace cannot resurrect capture with no viewer.
- The Pixel Spacetime worker keeps one coordinated command path. Its JSON subscription selects every committed pending Ticket automation row, including stream/keyframe work and `ticket_action_v3`, using the existing service identity and uncompressed text. A V3 priority consumer is independent of background/keyframe waiting, while subscription and reconnect polling still hand candidates to the same durable per-command dispatch ledger. Unacknowledged terminal results remain journaled; after acknowledgement, bounded TTL tombstones continue to own those command ids so stale pending scans can re-acknowledge them without another physical action. Only acknowledged tombstones are pruned; active, running, uncertain-registration, and unacknowledged entries cannot be silently evicted or physically replayed. Polling is reconnect/catch-up recovery and remains the sole terminal projection/acknowledgement path, not the warm command path. Start-before-keyframe ordering and the 75 ms active lane remain intact; the compact command signal and one-second desired-state read keep idle polling bounded without creating unchanged durable writes.
- Reload should replace same-viewer sockets and reach a visible frame from the active stream quickly.

Control-code cleanup paths:

- Public `ticket_remote` does not send `control_exit`, `reset_ticket`, or user tap/key commands for the request flow.
- The Pixel treats popup/result close as one mandatory root-only return-to-raw path. It must not use `FRESH_RESET`, `am force-stop`, navigation back to Orchestrator, accessibility clicks, accessibility text entry, or software/screenshot fallbacks for normal request completion.
- The cleanup path distinguishes raw ticket detail, the ticket-list card, the keyboard/input popup, generated control-code Aztec/result screen, and other known ViVi states. The healthy generated-result close uses two fresh cleanup-scoped rooted H.264 visual classifications; each exact sample has its own probe id and may request one coalesced immediate independent frame, after which the scheduler starts a new one-second period. The overall cleanup proof remains bounded and still requires two distinct consecutive raw-ticket samples. Unknown or ambiguous visual evidence fails closed; there is no ViVi hierarchy fallback. It closes the generated-result badge X using current detected bounds, then accepts only fresh visual ticket-detail proof; the ticket-header X and yellow registration control are never cleanup targets.
- Every success, failure, explicit close/expiry cancellation, and prepare/submit normalization path runs the same return-to-raw routine. For generated ViVi control-code success, that routine starts only after `ticket_remote` acknowledges requester-browser capture of the generated stream frame. Pixel-image acknowledgement is not a ViVi control-code path. A successful healthy cleanup emits `ticket_state_event(raw_ticket)` only after two agreeing fresh visual detail samples and a fresh raw-ticket frame. A failed cleanup records attention-needed while keeping the stream available and public input blocked.
- A durable `control_exit` remains actionable after the last viewer disconnects. Pixel must close a leftover ViVi popup/result without restarting capture, then return health to the prior inactive session state; disconnect must not turn the command into an acknowledged no-op.

Ingress behavior:

- `ticket_phone_bridge` reaches the Pixel privately and kitty-gration owns the only public Ticket ingress. The Pixel does not ship or supervise `cloudflared`.
- The durable orchestrator toggle controls whether `ticket_screen` may auto-start. Browser explicit Stop stops the stream session but does not turn this orchestrator toggle off.
- ViVi/Ticket state, navigation, card selection, registration geometry, public-open proof, active recovery, and control-code target geometry use only on-demand rooted H.264 visual observations. Two distinct fresh samples must agree before a state or geometry is accepted; unknown evidence fails closed. The Ticket service has no ViVi `uiautomator dump` entry point, does not request Ticket Accessibility snapshots, and does not retain hierarchy bytes in state memory. The guarded `uiautomator` wrapper remains callable only through the exact Rigas Satiksme dump path for that separate workload. Legacy ViVi hierarchy parser code may remain temporarily for TTL compatibility, but receives no runtime hierarchy source and therefore cannot authorize a Ticket action.
- Public-open and extended recovery use the same visual observation shape. A proved detail can complete readiness; a proved ticket list may supply one bounded typed target followed by a new two-frame detail proof. Registration journeys use only the registration-control target, while activated-detail and control-code recovery use only the compact registered-status target. A generic card body is not an action target. Login, blocker, unreadable, ambiguous, or redesigned layouts remain fail-closed. The visual detector runs only for an explicit action/readiness request and never stores or exports frames, OCR text, ticket identifiers, or raw pixels.
- Public open first asks the V3 current-view detector for two agreeing fresh frames. A proved activated detail, unactivated detail, or ticket list is sufficient to keep viewing live; the passive foreground guard also keeps a visually proved list live and leaves navigation to an explicit Ticket action. Stream readiness does not require legacy hierarchy, the legacy Aztec-only classifier, Back geometry, control-button geometry, navigation, or any phone mutation. Login, blocker, unknown, and conflicting results remain fail-closed. The explicit Ticket actions retain their stricter mutation geometry and terminal-proof contracts. The top-right header button is not a control-code cleanup target.
- Public `ticket_remote` must restart its phone reconnect loop whenever a new authenticated video viewer arrives and the relay is desired but not actively reconnecting. A stale desired state after phone reboot must not leave the public page waiting forever for the phone bridge.
- `ticket_phone_bridge` must not expose stale ADB forwards after reboot. It waits for `sys.boot_completed=1`, proves Pixel `/api/v1/health` over the forwarded port, and kills/recreates the local proxy when health probes fail or turn into EOF.
- `ticket_remote` clears cached config and cached frame state when the phone bridge disconnects. A newly opened browser video socket must not receive an old pre-reboot config unless the phone is currently connected and the config is fresh.
- The public server serves the current ticket app HTML for any non-reserved GET path. `/api/...`, `/static/...`, and `/admin...` remain strict/reserved.

The ticket component still follows the stack-wide operation model in [Pixel Stack Architecture](./PIXEL_STACK_ARCHITECTURE.md): `redeploy_component ticket_screen` refreshes the Pixel-side ticket surface, while public bridge/page deploys are separate.

For the public `ticket.jolkins.id.lv` path, Cloudflare Access terminates in front of `ticket_remote`. The browser talks to `ticket_remote`; `ticket_remote` relays video and queued control-code jobs privately to the Pixel through `ticket_phone_bridge`. Public socket identity should be visible in `ticket_remote` health, and the relay identity/page version should also be visible in Pixel `streamPipeline` health.

All authenticated linked viewers may receive the live video stream at the same time. There is no public private-control mode: viewers cannot claim the phone, tap the stream, or type into ViVi directly. A control-code requester receives only their private generated result, while other viewers continue seeing the shared raw ticket stream and may briefly see the real phone automate the request. A viewer reload or decoder reset must not restart or starve the shared phone stream for other authenticated viewers.

ViVi recovery launches `com.pv.vivi/.MainActivity` through the normal app intent and a root `am start` fallback. The fallback is required for post-reboot recovery because Android may leave Messages, Orchestrator, or another app in foreground while the ticket service is already ready.

ViVi authorization is a recoverable state only for the known existing-account login surface: email field, `Parole` field, `IEIET`, and `TURPINĀT BEZ AUTORIZĀCIJAS`. When that surface appears, Pixel reads credentials from `/data/local/pixel-stack/conf/apps/ticket-screen-vivi-login.env`, which must be outside git and mode `600`, with `VIVI_LOGIN_EMAIL` and `VIVI_LOGIN_PASSWORD`. The service enters the email only if the visible email differs, types the password directly into the password field, refreshes the `IEIET` target after the keyboard shifts the screen, taps `IEIET`, then waits for the login surface to disappear before resuming normal ticket-list recovery. Registration/profile/contact-detail surfaces and ViVi account/device-link mismatch dialogs after authorization are attention-needed states; the automation must not continue through them, dismiss them, or guess user details. The password must never be included in logs, health, screenshots metadata, fixtures, or support bundles; public health exposes only whether credentials were configured plus redacted login status/reason.

ViVi ticket-list recovery is date-aware. It parses visible time-ticket cards, ignores expired cards, prefers a card valid on the current date with the latest end date, and only chooses the soonest upcoming card when no current card exists. New-registration journeys open the selected ticket through its detected yellow `Reģistrēt biļeti` control. Activated-detail and control-code journeys require that same resolved card to expose one unambiguous compact registered-status target. Generic parent-card bounds are identity evidence only and are never tapped. Every activated journey must end in a fresh `TICKET_DETAIL` proof with the Aztec graphic; if the required typed target is absent or duplicated, the operation fails closed. Upcoming-card selection is surfaced as a warning-style recovery action (`open_upcoming_time_ticket_card`) in health events. The old first-visible-card rule is not valid for time tickets, because an expired cached card can appear above the fresh purchased ticket.

Public ticket verification is a public-viewer-only root-sourced health contract, not a screenshot-only check and not an RS Telegram acceptance gate. A pass requires both an authenticated Brave page drawing the live ticket and matching Pixel/relay health within a 15-second, 500 ms poll budget. Pixel must report `sessionState=live`, `streamActive=true`, `streamVerdict=live`, `ticketState.state=live`, `viviState.state=TICKET_DETAIL`, `visibleFrame.lastFrameAgoMillis<=1500`, and active rooted hardware H.264 capture. The public relay must report the phone connected, at least one active video client, a configured current stream, and `directStream.lastFrameAgoMillis<=1500`. Browser canvas evidence proves what the user saw, but it never overrides Pixel root state. If the canvas shows a ticket while Pixel or relay health is degraded, the result is `public_ticket_split_brain`, not success.

## 6. Health Counters, Events, And Measurement Caveats

The ticket session state machine uses bounded user-visible states: `starting`, `live`, `control_transition`, `control_exit`, `soft_recovery`, `needs_attention`, and `stopped`. Public pages should present control-code request progress separately from the stream state as `queued`, `running`, `succeeded`, `failed`, `expired`, or `closed`. Active transition states have a one-second budget. If the stream is active, recovery is not running, and ViVi is already on ticket detail, health reports `live` rather than staying stuck in `recovering`.

Important health surfaces:

- `serviceReadiness`: durable ticket-service toggle state, last ensure result and age, local ticket server reachability, tunnel readiness, and component status.
- `streamPipeline`: clients, configured/running state, frame envelope, stream epoch, frame sequence, quality profile, configured size/bitrate, recent frame/keyframe byte sizes, estimated send bitrate, encoded/sent/keyframe counts, dropped frames, slow writes, closed slow clients, replaced clients, and secure-window bypass state.
- `streamVerdict` and `visibleFrame`: the fast public-health verdict and recent rooted frame age; public verification requires `streamVerdict=live` and `visibleFrame.lastFrameAgoMillis<=1500`.
- `rootCapture`: support, active state, size, bitrate, fixed one-FPS target, frame counts, restart counts, restart reasons, last restart age, and suppressed restart requests. The legacy `ffmpeg` health object, if present, reports removed/unavailable only.
- `hardwareH264`: root capture availability and active state for the current production capture path, including fixed one-FPS cadence, `frameDependencyMode=all_intra`, deadline misses/skipped ticks, current interval, complete-frame liveness, and the count of rejected unexpected deltas. Public verification requires `hardwareH264.active=true` and `hardwareH264.state=active`; configuration and health prove the intended media contract, while physical freshness, thermal, memory, and browser paint still require device-matrix verification.
- `startupTrace`: the latest public stream startup timeline. The public relay trace follows authenticated prewarm, video socket open, Spacetime command write/dispatch, phone config/health/ticket-state events, first relay keyframe receipt, first successful viewer-writer keyframe/frame, and browser first-rendered-frame. Browser navigation, decoder configuration, first decode, and first canvas draw also carry the browser's source epoch and monotonic-performance timestamps. The phase `at` and `elapsedMillis` fields intentionally remain server receipt time; browser-performance deltas, Pixel-uptime deltas, and server-receipt deltas are evaluated within their own clock domains and are never subtracted across clocks. A private video socket may make the serialized immediate local session request before the durable start command reaches Pixel, so the trace preserves that actual causal order and never backdates command receipt. Correlation refresh is passive and never cancels or restarts a media connection. In the rare overlap where navigation B replaces A while A's private handshake is already in flight, media still proceeds, but B's Pixel segment may remain incomplete until the next normal private connection. Required Pixel startup markers transfer through a fixed-capacity, five-minute in-memory retained lane whose background sender cannot delay command handling; the newest startup replaces older retained startup generations, a worker reconnect returns undelivered messages to the phone outbox, and latest-ticket final markers retain their prior higher-priority identity. That capacity applies only to startup diagnostics: functional ticket-state and control/RS result, progress, and cleanup messages retain their existing TTL-based retry semantics independently and are delivered first; startup diagnostics never displace them. The Pixel trace follows phone session start, wake phases, ticket-ready proof, root H.264 start, config send, keyframe request, first encoded keyframe, and first visible frame sent. Both traces expose phase durations, the last phase, completion, and whether the 5-second public-open target was exceeded.
- `brightnessGuard`: active state, safe target percent, current display/panel values, last enforcement age, failure count, last reason, and message. A parked message means touch brightness currently owns panel brightness.
- `actionPanelDarkLease`: current action owner, active/age state, last independent zero-confirmation age, cumulative failure count, latest safe failure token, physical-touch preemption, and release reason. No panel path, raw command, pixels, coordinates, or touch details are published.
- `controlCodeRequest`: active state, last request id, digit count, command owner/app/flow, last rejected command envelope/reason, status, reason, total duration, phone phase timings, root-observation time, visual-marker time, result-delivery time, marker delivery state, duplicate result replay count, cleanup state, and completion age.
- `rigasSatiksmeBatch`: current or last RS batch id, status, active request id, job count, completed count, last per-request result id/status/reason, cancel reason, phase timings, and completion age. This is the RS reconciliation health surface; ViVi `controlCodeRequest` is not RS truth.
- Public `controlCodeRelayPreparation`: latest relay preparation result, duration, direct phone-session start status, socket-connected status, timeout, and completion age for public bridge control-code dispatch.
- `pixelTicketStateEvent`: latest Pixel-authoritative ticket state event, event sequence, request id, stream epoch, frame sequence, minimum frame sequence, reason, and age. Public/database/browser state should mirror this event stream and ignore stale lower-sequence events.
- `ticketState`: current bounded state, state age, last reason, over-one-second transition detail, and ViVi hard-reset count/reason.
- `viviState`: fresh Pixel app-state proof with state, source, reason, and observation age. Public verification requires `TICKET_DETAIL`; stale memory or inconclusive `UNKNOWN_VIVI` is not a public success source.
- `automation`: root-only automation mode, root-readiness result/age, and redacted ViVi login recovery status. It may report that login credentials are configured and the last login status/reason; it must not expose the login email or password.
- `loading`: most recent browser loading completion and over-budget phase/duration.
- Public relay `page`: latest HTML version, cache policy, and last client page version. Pixel health has no page/bootstrap/cache fields.
- `recentEvents`: server-side lifecycle, recovery, client, and input events.
- `recentClientTelemetry`: browser-side startup, media decode, visible-frame, watchdog, and socket events.
- Public relay `/api/v1/health.controlKeyframes`: historical keyframe-pulse counters plus sent cached keyframes, phone keyframe requests, and last pulse age. New control-code requests must not reintroduce controller-only video ownership.

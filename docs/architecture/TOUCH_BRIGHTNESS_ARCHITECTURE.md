# Touch Brightness Architecture

This is the canonical contract for Pixel touch brightness. Read it before changing phone automation, ticket brightness guards, root input monitors, screen wake behavior, or stream capture.

## 1. Ownership Contract

Touch brightness owns the physical panel brightness whenever the Pixel touch brightness toggle is enabled.

- Panel sleep means the Android display remains awake and interactive, while the real backlight panel brightness is written to `0`.
- While `panel_sleep` is active, two pixel-transparent, non-touchable windows request window brightness `0`: the existing one-pixel application overlay and a full-display accessibility overlay whose surface remains completely transparent. The distinct window types provide defense in depth during unrelated Android display-policy handoffs. Neither changes captured pixels nor intercepts input. The runtime grants the application overlay app-op through root, removes both shields before every physical visible restore or screen-off suspension, and refuses to complete a restore if either removal fails. Enabled runtime stops preserve the requested shield state so a recreated accessibility service and supervisor adopt it without a bright handoff gap; explicit disable removes both before restoring brightness. Raw panel writes remain the authority and fallback if a shield cannot be shown.
- Panel sleep is not Android screen-off, doze, keyguard, or a black accessibility overlay.
- The Android app keeps a screen wake hold active while panel sleep is active so normal app processing, ViVi rendering, ticket capture, and health updates continue.
- Restoring visible brightness after panel sleep must restore both Android display brightness and raw panel brightness. A visible wake or restore is not valid if Android display brightness remains at `0`, even when the raw panel file briefly reports the expected visible value.
- Destroying or replacing the supervision service while touch brightness remains enabled releases runtime jobs without restoring visible brightness or clearing the saved visible restore state. On the next start, an existing saved restore state identifies a restart: the runtime requests panel brightness `0` before readiness preparation and preserves the saved state even when preparation enters error backoff. The early clamp is best-effort so readiness preparation can repair transient root or sysfs failures. Explicitly disabling touch brightness still restores visibility and clears the saved state.
- Visible restore must actively reassert the Android display brightness and raw panel brightness until the post-restore read agrees with the saved or fallback target, then fail explicitly after a bounded retry budget if the panel remains dark or mismatched.
- The public state for this mode is `panel_sleep`. Old stored values such as `blackout_idle` and `dimmed` are compatibility aliases only.

The black accessibility overlay is legacy cleanup surface only. Normal touch brightness sleep must never show it, because stream capture would also see that black overlay.

## 2. Physical Input Sources

Root input monitors are the source of truth:

- `AndroidRootTouchMonitor` watches the selected hardware touchscreen device and emits physical display touch counts.
- `AndroidRootPowerKeyMonitor` watches the physical power-button device, preferring `gpio_keys`/`gpio-keys` over fingerprint fallback devices.
- Both startup readiness and live input-source monitors enumerate the existing `/dev/input/event*` nodes and query each node directly. Neither depends on `getevent`'s global `/dev/input` watcher, because that watcher can fail while the individual rooted device nodes remain healthy and readable.
- Remote browser taps, ADB `input tap`, accessibility actions, and other software input do not count as physical display touch and must not reset the timer.
- Root-confirmed physical display touch always wins over software/non-touch suppression. Non-touch suppression only applies to touch-like events that do not have raw physical touchscreen evidence.

The panel sleep timer is exactly two minutes. It starts when touch brightness enters visible idle, and it restarts when the last physical display touch is lifted or when the power button wakes the panel from panel sleep.

## 3. State Flow

Normal flow:

1. Touch brightness starts while Android is interactive.
2. The panel stays visible at the saved brightness and starts the two-minute physical-touch timer.
3. A physical touch before the deadline keeps or restores visible brightness.
4. When the last physical touch is lifted, the two-minute timer starts again.
5. If the timer expires with no physical touch, the app writes physical panel brightness `0`, keeps Android awake, and publishes `panel_sleep`.

Wake flow:

- Physical display touch while in `panel_sleep` restores saved visible brightness immediately and keeps the screen awake.
- Physical power-button press while in `panel_sleep` restores saved visible brightness and starts a short wake rebound window.
- If Android briefly processes that power-button press as screen-off, the rebound path sends `KEYCODE_WAKEUP`, restores visible brightness again, and continues the two-minute timer.
- A screen-off transition from `panel_sleep` without an actual root power-button event is not treated as physical intent. The runtime forces Android and raw panel brightness to zero before waking the display for continued rendering, reasserts zero afterward, and marks the resulting screen-on as non-touch so it cannot restore visible brightness. Only an observed power-button press or physical touch may enter visible mode.
- Power-button presses outside `panel_sleep` are not hijacked; ordinary Android power behavior remains available.

## 4. Ticket Guard Alignment

When touch brightness is enabled, the ticket brightness guard is parked.

- Ticket code must not write panel brightness, restore ticket brightness, or own a display-bright wake hold while touch brightness owns the panel.
- Ticket code may keep a CPU-only partial wake hold while touch brightness owns the panel; display wake/brightness remains touch-brightness-owned.
- Ticket root input and wake paths must mark software/non-touch input through `PhoneAutomationServiceBridge` before and after the root action so touch brightness can reassert panel sleep immediately. Ticket-prefixed non-touch events are authoritative only when no active physical touch is present: if a misclassified software touch has already pushed runtime into visible idle, the runtime cancels that timer and returns to `panel_sleep` instead of waiting two minutes, but non-touch work must not clear or override an active root-confirmed physical touch. Long bulk root scripts that can switch apps or run delayed taps must continue publishing non-touch intent while active, currently every 250 ms, so the 100/250/500/1000/1500 ms runtime reassertion bursts keep covering the full transition instead of only script start/end.
- Ticket control-code automation taps are not real user taps. While touch brightness owns the panel, control-code open/type/submit/cleanup scripts must hold the raw panel brightness at `0` before, during, and after the operation, and should avoid Android brightness-setting writes on the hot path when direct panel sysfs writes are available. Physical display touch still restores visible brightness through the normal wake flow.
- Unified Ticket v3 and control-code actions use one action-scoped panel-dark lease rather than independent four-second non-touch windows. The lease is acquired inside the shared phone-mutation lane before ViVi launch and stays active, while that lane remains owned, through waits, navigation, registration, terminal visual proof, keyboard-clamp release, and at least 2.5 seconds after the latest possibly dispatched mutation. Visual confirmation overlaps that convergence interval; finalization waits only its remainder before a fresh exact-zero check and identity-proved helper shutdown. It writes raw panel zero every 5 ms and independently confirms zero every 250 ms. The runtime publishes its root-confirmed physical-touch state through the bridge; a physical touch stops the helper synchronously at the next mutation boundary or within the 20 ms monitor cadence, including during the final tail. Every control-code ViVi launch, tap, typing script, submit, recovery input, and result-close input crosses that boundary and is marked possibly dispatched before Android receives it. If the last exact raw-zero proof is more than two seconds old at a mutation boundary, that boundary waits for an already-running verifier or performs one bounded fresh exact helper-identity/raw-zero verification; only a newly fresh proof may continue. Physical touch is checked before and after that verification and always wins, while helper loss, a nonzero read, or unavailable verification fails closed. Before any phone dispatch the action stops safely; after a possible dispatch it returns attention-needed and cannot replay that attempt.
- The final tail ends with a new exact raw-zero read. Finalization then freezes periodic verification, requires the complete fresh helper-identity/raw-zero mutation gate while the helper identity files still exist, proves identity-checked helper shutdown, and performs a separate synchronous physical-touch check after shutdown while the mutation lane is still held. Shutdown deliberately removes the helper identity files, so it must never invoke the helper verifier afterward; a slow successful shutdown cannot become false helper-identity loss merely because the pre-stop proof ages during cleanup. The root touch monitor remains active through shutdown and the post-stop check closes its last scheduler window. A successful v3 journal/terminal, control-code raw-ready event, cleanup success, and fast-ready state may be published only after all of those proofs succeed. The local control-code cleanup checkpoint and private visual signatures remain intact until that boundary; an unsafe finalization keeps the checkpoint closed so the next request requires explicit visual recovery. Scheduled control-exit recovery acquires its own lease inside the same phone lane. When the phone has already returned to an ordinary Aztec detail but only the durable checkpoint remains stale, an automatically requested `prove_current` becomes that explicit recovery: it cannot be superseded by a later action, enters the same phone lane and panel lease, performs no ViVi launch or input, and requires both two fresh strict `RAW_TICKET` frames and two fresh typed activated/unactivated-detail frames with a valid static anchor and control geometry. Its success is neither journaled nor published before finalization. After the tail it rechecks the action generation, current encoded keyframe, absence of a control request and keyboard lease, then clears the checkpoint synchronously; any mismatch retains the fence. Ordinary `prove_current` remains lane-free and read-only. A provisional successful v3 proof is also revalidated after the tail against its action, generation, stream epoch, frame sequence, and latest keyframe before it can retain a slider or switch. Physical-touch preemption, lost zero, unavailable final verification, stale visual proof, or unproved helper shutdown overrides any provisional success. The active lease and non-touch suppression are cleared before the lane becomes available to the next phone action.
- Action lease cleanup is process-safe as well as coroutine-safe. A dedicated root worker remains owned for the Ticket service lifetime because Magisk can tear down descendants when a short app-owned `su` session closes. It creates a root-only per-action launch marker, starts the helper directly in a descriptor-closed `nohup` child of that persistent worker, and acknowledges as soon as the shell supplies a numeric background PID without duplicating acquisition's readiness polling. No `setsid` hop is used: production lifecycle telemetry showed that the extra hop could report a successful outer launch without ever entering the owner-bound helper, while the persistent worker already supplies the stable root session. The child enforces its own monotonic 90-second deadline. Normal success, failure, cancellation, timeout, and service destruction release it in a non-cancellable finalizer. The finalizer retains the launch marker while cancelling and joining the launcher for longer than the launcher's own hard bound, then uses a separate root executor to validate the exact helper token, PID, process start time, marker, and owner arguments. Exact process checks read each NUL-delimited cmdline argument with the Android shell builtin and require separate marker, token, owner-PID, and owner-start matches; global scans read process start time only for a complete candidate and never fork a `grep` per argument or process. When readiness is absent the finalizer sends a bounded TERM/KILL sequence, proves the original process is gone, and only then removes both files. The root helper also checks the exact Android owner PID/start time and launch marker on every write. After its first successful zero write, it creates the readiness file containing only process identities and start times. Acquisition requires the short launcher to finish successfully, then validates that identity and fails closed until two separate raw-zero confirmations agree; a background PID, pre-existing dark panel, or stale readiness record alone cannot authorize an action. Per-token root-only lifecycle files retain only an allowlisted startup stage and a numeric shell exit code; verifier output revalidates those values before the existing health object publishes them alongside the last verifier classification, exit code, and duration. No command, path, ticket content, or raw root error is exposed. Normal stop and capped startup cleanup remove all lifecycle files. Service startup kills exact validated helpers even if the old Android owner has died, preserves malformed uncertain identity records as a startup failure, and refuses pending Ticket commands until cleanup succeeds.
- The helper's five-millisecond hold cadence uses one per-token FIFO created under the same root-only directory and `umask 077`. The child proves that path is a FIFO, opens it read/write on a private descriptor, and uses mksh's built-in `read -t0.005` timeout rather than spawning `usleep` or `sleep` every iteration. Helper, owner, verifier, exact-stop, and startup-cleanup process/brightness reads use shell built-ins where safe. Zero is still written before readiness, exact identity and owner checks are unchanged, and failure to create, prove, or open the FIFO stops before authorization. Helper exit, exact stop, and capped orphan startup cleanup all remove the FIFO.
- Once the raw panel already reads `0`, routine panel-sleep reassertions should stay cheap: the quiet guard verifies brightness on a 30-second cadence, skips the write when the panel is still dark, and uses a short sysfs-only hold only when a write is needed. Failed guard writes still retry quickly. Keep the longer hold for the initial transition into panel sleep and for visible restore, where Android or panel rebound is still being actively overcome.
- The ticket service may hide any stale black overlay defensively, but it must not use that overlay as a normal sleep mechanism.
- Remote ticket viewers should continue seeing live rendered ticket content while the physical Pixel panel is at brightness `0`.
- Ticket health reports the guard as inactive/parked with a message explaining that touch brightness owns panel brightness.

When touch brightness is disabled, the ticket brightness guard may use its normal safe dim behavior.

## 5. Implementation Anchors

Primary code paths:

- `TouchBrightnessRuntime.kt`: two-minute timer, panel sleep state, physical touch reset, non-touch reassertion bursts, power-button rebound, and visible brightness restore.
- `PanelSleepBrightnessShieldController.kt` and `PhoneAutomationAccessibilityService.kt`: coordinated transparent application/accessibility brightness shields that neutralize activity window-brightness overrides only during `panel_sleep`.
- `RootTouchMonitor.kt`: physical touchscreen discovery and touch-count tracking.
- `RootPowerKeyMonitor.kt`: physical power-button discovery and press events.
- `TouchScreenPowerController.kt`: ordinary wake and forced wake used during rebound; panel-sleep wake holds must use a non-bright/non-wake-causing display hold (`SCREEN_DIM_WAKE_LOCK`), not `SCREEN_BRIGHT_WAKE_LOCK` or `ACQUIRE_CAUSES_WAKEUP`.
- `PhoneAutomationBridge.kt`: software/non-touch input suppression events plus the minimal root-confirmed physical-touch active/timestamp projection shared into Ticket action safety.
- `TicketActionPanelDarkLease.kt`: bounded Ticket v3 owner lease, raw zero writer, independent confirmation, physical-touch preemption, owner-process self-termination, and exact-marker startup cleanup.
- `TicketStreamService.kt`: guard parking, non-touch root input/script marking, v3 action-wide panel-dark ownership and health, active long-script reassert heartbeats, rooted panel/display clamp wrappers around wake/app-switch/control-code scripts, hot-path sysfs-only panel clamps when available, and CPU-only ticket wake hold while touch brightness owns the panel.

An enabled touch-brightness runtime in persisted `STOPPED` or `ERROR` state starts immediately during supervision sync, even when Speedtest recovery owns its own lane. Only an explicit destructive touch-brightness `RESTART` requested by prerequisite recovery may remain deferred until the automation recovery lane is free. Ticket brightness fallback, read, and enforcement failures use the `ticket_brightness_` Spacetime trace allowlist.

Stable tests should cover the two-minute timer, physical touch reset, software-input non-reset, panel `0`, visible Android display brightness restore, restore verification that fails while Android display brightness remains `0`, non-touch panel-sleep reassertion, long-script non-touch heartbeats, power-button wake rebound, ordinary screen-off suspension, disable restore, and ticket guard parking.

- 2026-08-26: A stale panel-zero timestamp at a Ticket mutation boundary now triggers bounded fresh exact verification instead of failing solely because the periodic verifier was delayed. The stale proof itself never authorizes input; physical touch is checked on both sides of the refresh, and a nonzero panel, lost helper, or unavailable verifier still stops the action.
- 2026-08-26: The action panel helper no longer runs as one long `SuRootExecutor` command. Live read-only recovery showed that root session ending around five seconds could terminate the otherwise healthy clamp and fail the action while external sampling still read zero. A short descriptor-closed `nohup`/`setsid` launcher now hands off to an exact owner-bound helper with a monotonic 90-second deadline. A pre-spawn launch marker and post-launch readiness record let preemption, service replacement, final release, and startup cleanup scan and stop only the unique exact process without accepting a missing record as success.
- 2026-08-26: The first detached production proof failed safely before mutation. Review then found that the inner helper re-enabled `SIGHUP` after `nohup` had ignored it, matching that early session-lifetime failure. The helper now keeps hangup ignored while retaining INT/TERM/EXIT cleanup. Acquisition cannot count readiness until the short launcher succeeds, cancellation cleanup waits beyond the launch hard bound before its final exact scan, and privacy-safe launch exit/duration fields distinguish launcher failure from later helper loss.
- 2026-08-26: A second production proof returned launch exit `74` after 1.723 seconds without mutation. An exact device replay proved the child script itself, while a separate measurement showed that its parent launcher spent 1.715 seconds in the twenty nominal 25 ms readiness sleeps because each Android toybox sleep required an external process. The launcher now acknowledges the shell's numeric background PID immediately. - 2026-08-26: Ticket finalization now measures the 2.5-second convergence window from the latest possibly dispatched mutation.

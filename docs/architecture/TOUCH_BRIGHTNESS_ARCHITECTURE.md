# Touch Brightness Architecture

This is the canonical contract for Pixel touch brightness. Read it before changing phone automation, ticket brightness guards, root input monitors, screen wake behavior, or stream capture.

## 1. Ownership Contract

Touch brightness owns the physical panel brightness whenever the Pixel touch brightness toggle is enabled.

- Panel sleep keeps Android awake and interactive while the Pixel backlight driver is blanked with `bl_power=4`. A checked raw brightness `0` write preserves the existing Ticket action zero-verification contract. The gate, rather than repeated brightness requests, prevents Android brightness ramps from emitting light.
- The runtime owns the backlight blank gate. It does not create brightness override windows, change Android brightness settings to zero, or schedule dimming bursts. The previous application/accessibility shields and their slider suspension path are removed. The Pixel display driver forces emitted brightness to zero while blanked even when subsequent requests are positive; both `brightness` and `actual_brightness` may report the requested value, so they are not optical proof while the gate is closed. Driver behavior is documented in [Google gs_panel](https://android.googlesource.com/kernel/google-modules/display/common/+/refs/tags/android-16.0.0_r0.9/gs_panel/gs_panel.c) and was checked on the actual Pixel with positive requests remaining `br:0` in the driver.
- Panel sleep is not Android screen-off, doze, keyguard, or a black accessibility overlay.
- The Android app keeps a screen wake hold active while panel sleep is active so normal app processing, ViVi rendering, ticket capture, and health updates continue.
- Visible restoration prepares Android and raw brightness behind the closed gate, then writes and verifies `bl_power=0`. Readback must also prove the gate open; matching requested brightness alone cannot take an already-restored shortcut. When Android mode/value still match and display brightness is positive, restoration uses one raw request and unblank, without framework writes or a hold. Changed or unavailable Android state retains bounded convergence behind the gate; there is only one raw hold sequence. Post-restore checks still cover Android brightness, raw brightness, and an open gate. Explicit disable joins the old runtime writers before restoration and uses a safe visible fallback if no saved brightness exists.
- Destroying or replacing the supervision service while touch brightness remains enabled releases runtime jobs without restoring visible brightness or clearing the saved visible restore state. On the next start, an existing saved restore state identifies a restart: unless the same process retains an active physical visible window, the runtime requests panel brightness `0` before readiness preparation and preserves the saved state even when preparation enters error backoff. A retained window resumes with its remaining time; a new process has no retained physical grant. The early clamp is best-effort so readiness preparation can repair transient root or sysfs failures. Explicitly disabling touch brightness still restores visibility and clears the saved state.
- Visible restore must actively reassert the Android display brightness and raw panel brightness until the post-restore read agrees with the saved or fallback target, then fail explicitly after a bounded retry budget if the panel remains dark or mismatched.
- The public state for this mode is `panel_sleep`. Old stored values such as `blackout_idle` and `dimmed` are compatibility aliases only.

The black accessibility overlay is legacy cleanup surface only. Normal touch brightness sleep must never show it, because stream capture would also see that black overlay.

## 2. Physical Input Sources

Root input monitors are the source of truth:

- `AndroidRootTouchMonitor` watches the selected hardware touchscreen device and emits physical display touch counts.
- `AndroidRootPowerKeyMonitor` watches the physical power-button device, preferring `gpio_keys`/`gpio-keys` over fingerprint fallback devices.
- Both startup readiness and live input-source monitors enumerate the existing `/dev/input/event*` nodes and query each node directly. Neither depends on `getevent`'s global `/dev/input` watcher, because that watcher can fail while the individual rooted device nodes remain healthy and readable.
- Remote browser taps, ADB `input tap`, accessibility actions, and other software input do not count as physical display touch and must not reset the timer.
- Root-confirmed physical display touch always wins over software/non-touch suppression. Before restoring visibility, the runtime waits up to five seconds for every exact registered Ticket dark writer to prove shutdown; an unproved writer keeps the restore blocked. The helper registers before launch and rechecks the physical grant after registration, preventing a new helper from racing a visible restore. Non-touch suppression only applies to touch-like events that do not have raw physical touchscreen evidence. Non-touch events retain the touch-begin generation at emission, so a queued event cannot re-darken the panel after a complete physical tap. Non-touch reassertion runs in an owned job; visible restoration cancels and joins every pending dark writer, including an expired idle timer, before writing visible brightness. Root commands admit execution only after the Android shell PID/start identity is captured, and cancellation proves that exact command tree stopped before returning. Unproven cleanup fails the runtime instead of allowing a competing visible restore.

The physical visible window is 90 seconds. A real touchscreen contact grants it immediately and the last physical touch-up renews the full 90 seconds. Only physical touch renews it; browser input, app navigation, command cleanup, and screen-on events cannot extend it. The bridge publishes one monotonic deadline and generation for the runtime and every Ticket lease. Duplicate or older touch events cannot move that deadline backward. A physical side-button press revokes the grant immediately; a later release of the same held contact cannot reopen it.

## 3. State Flow

1. Enabled touch brightness starts in panel sleep with Android held awake.
2. A physical touchscreen contact restores visible brightness and grants the physical visible window.
3. The last finger lift starts the full 90-second countdown. Further physical contacts renew it.
4. Automated actions may start visibly during that window. A new physical tap interrupts pending Ticket automation and stops its exact dark helper before visibility is restored. Finger-up does not resume that attempt or replay dispatched input. Non-touch events leave the window unchanged.
5. At expiry, the runtime darkens the physical panel while Android stays interactive.
6. A short physical side-button press revokes visibility and immediately writes and verifies the persistent blank gate before raw zero. State bookkeeping remains in the owned non-touch writer. If visibility is being restored, raw-source revocation cancels and joins that exact visible writer before blanking. A subsequent physical tap joins pending dark writes before unblanking. Pressing the side button while already dark keeps it dark.

On the Pixel's Android 16 policy, enabled touch brightness owns `Settings.Global.power_button_short_press=0` (`SHORT_PRESS_POWER_NOTHING`). The root power monitor still observes the hardware key and requests panel sleep; Android does not turn off the display for that short press. The original setting, including its absence, is saved synchronously before acquisition, retained across enabled service restarts, and restored and verified on explicit disable. A failed policy change or restoration is reported and retains its recovery checkpoint. Long-press, double-press and volume behavior are unchanged.

Unexpected Android screen-off while panel sleep is active still follows the existing zero-before-wake recovery. An active physical visible window can recover screen-on without renewing its deadline. A screen-on event without physical visibility authority does not restore visible brightness. The old power-to-visible rebound and its timer are removed.

## 4. Ticket Guard Alignment

Ticket dark acquisition performs its two separate identity/readback confirmations inside one bounded root verification call, with 25 ms between observations. Only a complete pair reports acquisition success; no previous or partially successful pair carries forward. The app still independently proves launcher success, monitors physical-touch/visibility changes during verification, and checks the current authority before any input.

When touch brightness is enabled, the ticket brightness guard is parked. After exact helper/owner validation, darkness is proved by `bl_power=4`, or by the existing strict requested/actual zero checks when the gate is not blank. Positive requested brightness under the verified blank gate is not a loss of physical darkness. Missing or invalid gate state cannot substitute for strict raw-zero proof. Existing health fields named `lastZeroConfirmationAgoMillis` retain their key and now age the verified darkness proof; internal finalization uses `freshDarkProven`.

- The Ticket brightness guard must not compete with touch brightness by writing or restoring panel brightness or owning a display-bright wake hold. Ticket automation uses only the shared panel-dark lease described below.
- Ticket code may keep a CPU-only partial wake hold while touch brightness owns the panel; display wake/brightness remains touch-brightness-owned.
- Ticket root input and wake paths publish software/non-touch intent when acquiring their panel-dark protection and clear that suppression when releasing it. The shared helper covers the full operation; per-command reassertion jobs and completion events that could darken the panel again after human touch are not used. Clearing suppression only shortens its timestamp; it never emits another non-touch event. Other non-touch consumers retain the touch-brightness runtime's existing reassertion behavior.
- Ticket control-code automation taps are not real user taps. Outside the physical visible window, while touch brightness owns the panel, control-code open/type/submit/cleanup scripts must hold the raw panel brightness at `0` before, during, and after the operation, and should avoid Android brightness-setting writes on the hot path when direct panel sysfs writes are available. Physical display touch still restores visible brightness through the normal wake flow.
- Every action owns one lease in `dark`, `visible_window`, or `darkening` mode. An existing physical visibility grant permits a new action without a dark helper or zero proof. A new touch or renewed grant during that action preempts it permanently; pending input stops and exact helper shutdown releases the visibility blocker. On expiry or side-button revocation of the original grant, the same lease reacquires dark protection: the next mutation waits for two darkness confirmations, while a dispatched command has only the bounded darkening interval before failure cancels it. Helper launch and finalization share ownership so a released lease cannot spawn a late helper. Visible finalization reports its mode without fabricating `freshDarkProven`; dark finalization retains fresh darkness, convergence, and exact shutdown proof. Lost physical source or unproved helper shutdown fails closed. Private health reports the mode and remaining physical visible time.
- Registration invalidated by physical contact refreshes exact ticket, scene, and input proof after lift before its first dispatch. A completed stroke may obtain fresh post-lift success proof, but physical contact never authorizes a repeat of an ambiguous stroke. Observation and preparation retries are bounded. Read-only `prove_current` may restart its observation and watermark after lift under the same action and mutation generation.
- Unified Ticket v3 and control-code actions use one action-scoped panel-dark lease rather than independent four-second non-touch windows. The lease is acquired inside the shared phone-mutation lane before ViVi launch and stays active, while that lane remains owned, through waits, navigation, registration, terminal visual proof, keyboard-clamp release, and at least 2.5 seconds after the latest possibly dispatched mutation. Visual confirmation overlaps that convergence interval. In dark mode, finalization waits only its remainder before a fresh darkness check and identity-proved helper shutdown; the helper checks its exact owner and gate every 5 ms, writes raw zero only while the gate is not blank (plus the initial readiness write), and independently verifies darkness every 250 ms. The runtime atomically publishes root-confirmed touch availability, current contact, and a monotonic touch-begin count. Each lease records that count before launching; a new touch permanently preempts pending automation even if the finger is lifted before the next check. Acquisition, mutation, verification, and post-shutdown checks all compare the count. The lease touch monitor starts during acquisition, cancels an in-flight acquisition verifier before shutdown, and checks every 20 ms and command execution checks every 5 ms; these are scheduling intervals, not guarantees of completed helper shutdown. Physical contact stops further input for this action and starts bounded exact helper shutdown, including during the final tail. Every control-code ViVi launch, tap, typing script, submit, recovery input, and result-close input crosses that boundary and is marked possibly dispatched before Android receives it. If the last exact raw-zero proof is more than two seconds old at a mutation boundary, that boundary waits for an already-running verifier or performs one bounded fresh exact helper-identity/raw-zero verification; only a newly fresh proof may continue. Physical touch is checked before and after that verification and preempts the action; in dark mode, helper loss, a nonzero read, or unavailable verification fails closed. An unproved protection boundary stops before dispatch or returns attention-needed after a possible dispatch, and cannot replay that attempt.
- The shared command runner borrows an existing action lease without acquiring or releasing another helper. Standalone wake, launch, or recovery commands acquire the same lease inside their caller's already-owned phone-mutation lane and finish convergence before returning success. Loss of authority cancels in-flight command work; unsafe standalone completion stops the calling coroutine instead of allowing an ignored result or recovery fallback to replay input. Script completion is conservatively treated as the last possible mutation for convergence, since bulk scripts can dispatch near their end. Root scripts retain their separate child-process timeout; the retired per-command zero writer, stop files, post-write loop, heartbeat jobs, and unused zero-tail branch are deleted.
- In dark mode, the final tail ends with a new exact raw-zero read. Finalization then freezes periodic verification, requires the complete fresh helper-identity/raw-zero mutation gate while the helper identity files still exist, proves identity-checked helper shutdown, and performs a separate synchronous physical-touch check after shutdown while the mutation lane is still held. Shutdown deliberately removes the helper identity files, so it must never invoke the helper verifier afterward; a slow successful shutdown cannot become false helper-identity loss merely because the pre-stop proof ages during cleanup. The root touch monitor remains active through shutdown and the post-stop check closes its last scheduler window. A successful v3 journal/terminal, control-code raw-ready event, cleanup success, and fast-ready state may be published only after all of those proofs succeed. The local control-code cleanup checkpoint and private visual signatures remain intact until that boundary; an unsafe finalization keeps the checkpoint closed so the next request requires explicit visual recovery. Scheduled control-exit recovery acquires its own lease inside the same phone lane. When the phone has already returned to an ordinary Aztec detail but only the durable checkpoint remains stale, an automatically requested `prove_current` becomes that explicit recovery: it cannot be superseded by a later action, enters the same phone lane and panel lease, performs no ViVi launch or input, and requires both two fresh strict `RAW_TICKET` frames and two fresh typed activated/unactivated-detail frames with a valid static anchor and control geometry. Its success is neither journaled nor published before finalization. After the tail it rechecks the action generation, current encoded keyframe, absence of a control request and keyboard lease, then clears the checkpoint synchronously; any mismatch retains the fence. Ordinary `prove_current` remains lane-free and read-only. A provisional successful v3 proof is also revalidated after the tail against its action, generation, stream epoch, frame sequence, and latest keyframe before it can retain a slider or switch. Physical-touch preemption, lost zero, unavailable final verification, stale visual proof, or unproved helper shutdown overrides any provisional success. The active lease and non-touch suppression are cleared before the lane becomes available to the next phone action.
- Action lease cleanup is process-safe as well as coroutine-safe. A dedicated root worker remains owned for the Ticket service lifetime because Magisk can tear down descendants when a short app-owned `su` session closes. It creates a root-only per-action launch marker, starts the helper directly in a descriptor-closed `nohup` child of that persistent worker, and acknowledges as soon as the shell supplies a numeric background PID without duplicating acquisition's readiness polling. No `setsid` hop is used: production lifecycle telemetry showed that the extra hop could report a successful outer launch without ever entering the owner-bound helper, while the persistent worker already supplies the stable root session. The child enforces its own monotonic 90-second deadline. Normal success, failure, cancellation, timeout, and service destruction release it in a non-cancellable finalizer. The finalizer retains the launch marker while cancelling and joining the launcher for longer than the launcher's own hard bound, then uses a separate root executor to validate the exact helper token, PID, process start time, marker, and owner arguments. Exact process checks read each NUL-delimited cmdline argument with the Android shell builtin and require separate marker, token, owner-PID, and owner-start matches; global scans read process start time only for a complete candidate and never fork a `grep` per argument or process. When readiness is absent the finalizer sends a bounded TERM/KILL sequence, proves the original process is gone, and only then removes both files. The root helper, when dark-mode protection is required, also checks the exact Android owner PID/start time and launch marker on every write. After its first successful zero write, it creates the readiness file containing only process identities and start times. Acquisition requires the short launcher to finish successfully, then validates that identity and fails closed until two separate darkness confirmations agree; a background PID, pre-existing dark panel, or stale readiness record alone cannot authorize an action. Per-token root-only lifecycle files retain only an allowlisted startup stage and a numeric shell exit code; verifier output revalidates those values before the existing health object publishes them alongside the last verifier classification, exit code, and duration. No command, path, ticket content, or raw root error is exposed. Normal stop and capped startup cleanup remove all lifecycle files. Service startup kills exact validated helpers even if the old Android owner has died, preserves malformed uncertain identity records as a startup failure, and refuses pending Ticket commands until cleanup succeeds.
- The helper's five-millisecond hold cadence uses one per-token FIFO created under the same root-only directory and `umask 077`. The child proves that path is a FIFO, opens it read/write on a private descriptor, and uses mksh's built-in `read -t0.005` timeout rather than spawning `usleep` or `sleep` every iteration. Helper, owner, verifier, exact-stop, and startup-cleanup process/brightness reads use shell built-ins where safe. Zero is still written before readiness, exact identity and owner checks are unchanged, and failure to create, prove, or open the FIFO stops before authorization. Helper exit, exact stop, and capped orphan startup cleanup all remove the FIFO.
- The quiet guard checks the backlight gate every 30 seconds and skips writes while it remains blanked. Gate loss triggers a checked blank/zero write; failures retry at 500 ms under the existing failure limit. Screen-on and non-touch events reassert the gate because a real display power change can reset it. No scheduled dimming bursts or dark hold loops remain in the touch runtime. Ticket action helpers retain their exact ownership, requested-zero proofs, and bounded lifetime.
- The ticket service may hide any stale black overlay defensively, but it must not use that overlay as a normal sleep mechanism.
- Remote ticket viewers should continue seeing live rendered ticket content while the physical Pixel panel is at brightness `0`.
- Ticket health reports the guard as inactive/parked with a message explaining that touch brightness owns panel brightness.

When touch brightness is explicitly disabled, standalone wake and recovery commands retain the normal Ticket brightness policy without acquiring a panel-dark lease. Missing state or a lost monitor while enabled is not treated as disabled. Existing admitted action leases still enforce their own safety contract.

The V2 helper writes only its launch identity, readiness identity, and wait FIFO. Launch and verification exit status remain in health; per-stage and exit telemetry files are retired. Startup cleanup and exact shutdown still remove any such files retained from V1.

## 5. Implementation Anchors

Primary code paths:

- `TouchBrightnessRuntime.kt`: 90-second physical visibility, persistent panel blanking, side-button darkening, quiet guard, and visible brightness restore.
- `PanelSleepBrightnessShieldController.kt` and `PhoneAutomationAccessibilityService.kt`: coordinated transparent application/accessibility brightness shields that neutralize activity window-brightness overrides only during `panel_sleep`.
- `RootTouchMonitor.kt`: physical touchscreen discovery and touch-count tracking.
- `RootPowerKeyMonitor.kt`: physical power-button discovery and press events.
- `TouchScreenPowerController.kt`: ordinary wake and forced wake used during screen-off recovery; panel-sleep wake holds must use a non-bright/non-wake-causing display hold (`SCREEN_DIM_WAKE_LOCK`), not `SCREEN_BRIGHT_WAKE_LOCK` or `ACQUIRE_CAUSES_WAKEUP`.
- `PhoneAutomationBridge.kt`: software/non-touch input suppression, the physical visibility deadline and generation, atomically published root-confirmed touch state, and retained touch-begin count.
- `TouchPowerButtonPolicyController.kt`: durable ownership and exact restoration of Android short-press policy.
- `TicketActionPanelDarkLease.kt`: bounded Ticket v3 owner lease, raw zero writer, independent confirmation, physical-touch preemption, owner-process self-termination, and exact-marker startup cleanup.
- `TicketStreamService.kt` and `TicketPanelDarkCommandRunner.kt`: guard parking, one shared lease for action and standalone command protection, bounded command cancellation, finalization, health, and CPU-only ticket wake holds.

An enabled touch-brightness runtime in persisted `STOPPED` or `ERROR` state starts immediately during supervision sync, even when Speedtest recovery owns its own lane. Only an explicit destructive touch-brightness `RESTART` requested by prerequisite recovery may remain deferred until the automation recovery lane is free. Ticket brightness fallback, read, and enforcement failures use the `ticket_brightness_` Spacetime trace allowlist.

Stable tests should cover the two-minute timer, physical touch reset, software-input non-reset, panel `0`, visible Android display brightness restore, restore verification that fails while Android display brightness remains `0`, non-touch panel-sleep reassertion, remembered brief touches during acquisition/verification/shutdown, shared command cancellation and convergence, power-button wake rebound, ordinary screen-off suspension, disable restore, and ticket guard parking.
